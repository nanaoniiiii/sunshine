## 2. 目标与当前结论

目标是 Android 11+ 上，结合 Sunshine、Moonlight 和 Shizuku，使用三星原生 DeX 独立第二屏，无需 HDMI，支持准确输入、主屏面板关闭和尽可能高的实际帧率。

已在 SM-G986U1 / Android 13 无 HDMI 启动真正的原生双屏 DeX；系统 Display 2、实际 1920×1080 / 60Hz。该固件未实现 1440×3168 / 120Hz 的原生 DeX，不能将客户端请求或编码帧率等同于源显示模式。

最新改为 SM-T970 平板做主机，在普通虚拟屏上确认了一个错误限帧原因：系统报告 60Hz，而新纹理实际持续约 120fps；旧代码据报告值将编码器限制为 60。现在根据真实 SurfaceTexture 时间戳确认更高源节奏，再重配编码器。单路 2K / 120fps 的 90 秒采样编码 FPS 窗口中位数 **118.64**，整个区间平均约 **115.81fps**，新增队列丢帧、最终发送失败、输入额度超时均为 0。包含启动低帧率，且测试画面简单，不能称全程满帧或接收端零丢包。

**尚未完成最终验收**：最新平板主机的三端同连、关闭主面板后的 120fps、小时级运行及高动态大帧恢复。旧手机原生 DeX 三端曾有约 30fps 和高熵启动期丢帧，这些仍是待解决项。

## 3. 关键实现与入口

| 功能 | 主要文件 / 行为 |
| --- | --- |
| 无 HDMI 原生 DeX | `service/SamsungLocalDex.kt`、`NativeDexMirror.kt`、`service/headless/*.java`：本机 DeX for PC 接收端、认证、WFD 保活与 SurfaceControl 镜像 |
| 坐标与输入 | `CaptureGeometry.kt`、`engine/InputBroker.kt`：区分真实输入显示和采集画布，反算缩放、边缘与指针映射 |
| 真实源帧率 | `SourceCadenceTracker.kt`、`SunshineFrameDispatcher.kt`、`SunshineEngineClient.kt`：纹理时间戳连续两个稳定窗口学习，换源重置，遵守接收端与配置上限 |
| 编码链路额度 | `FrameSubmissionBudget.kt`：每路最多 4 个未完成输入，以微秒 PTS 精确回收；350ms 兜底超时 |
| 逐客户端队列 | `native/fresh_video_queue.h`：8 帧 / 8MiB / 普通 80ms，参考链与 IDR 恢复隔离；大帧保护有界 |
| UDP 与 FEC | `native/datagram_batch.h`、`datagram_retry.h`、`udp_batch_io.h`、`android/prepare_source.py`：每路视频线程、FIFO 批次门、部分成功只重试未发送后缀、NEON FEC |
| 自适应回升 | `native/video_controls.h`、`network_policy.h`：恢复逻辑接入实际取编码命令路径；默认关闭，手动码率退出自适应 |
| 主面板控制 | `VirtualDisplayUserService.kt`、`SunshineRuntimeManager.kt`、API 与实验设置页：仅操作本应用管理的独立第二屏，退出恢复 |
| 旧 Shizuku | `VirtualDisplayUserService.kt` 同时保留 Context 和无参构造；平板 Shizuku 12.9 无参实例化已实机通过 |
| 电源与生命周期 | `StreamingPowerManager.kt`、`SunshineEngineService.kt`：引擎前台服务、Wi-Fi 锁、用户服务所有者死亡清理，避免旧进程积累 |

DeX 路径依赖设备自带兼容的 `com.sec.android.app.dexonpc` 系统组件、64 位 Shizuku 用户服务，以及本机 Wi-Fi 地址。系统主屏仍需确认“Sunshine Local DeX / 立即开始”。运行时加载本机系统 DeX 的兼容库，加载后删除临时副本，不将厂商二进制打包分发。

没有通过假冒 HDMI 或启用 Standalone 实现。早期直接 WFD Binder 原型被系统签名权限拒绝；当前成功路径是自写的 DeX for PC 本机接收端。旧原型文件仍保留作历史工具，生产实现以应用 `service/headless/` 为准。

原生测试输出在 `native/.official-build/<ABI>/`，需推送到明确选定设备的临时目录执行并记录退出码。11 项为：audio_packetizer、canvas_policy、datagram_batch、datagram_retry、encoder_selection、fec_scalar、fec_vector、fresh_video_queue、native_audio、network_policy、video_policy，各以 `_test` 结尾。

主机 API 根地址是 `http://<HOST>:47990/api/`。先 GET `runtime/sessions`、`virtual-screen`、`diagnostics`、`config`，避免影响用户现有会话。主要操作：

| 方法 / 路径 | 参数与用途 |
| --- | --- |
| POST `virtual-screen/create` / `virtual-screen/exit` | `{}`，创建或退出第二屏 |
| POST `virtual-screen/panel` | `{"off":true}` 关闭物理主面板；false 恢复。不能等同于系统 KEYCODE_SLEEP |
| POST `runtime/sessions/<id>/disconnect` | `{}`，只结束明确的测试会话 |
| POST `runtime/sessions/<id>/bitrate` | `{"bitrate_kbps":20000}`，手动设置并退出自适应 |
| POST `runtime/sessions/<id>/adaptive` | `{"enabled":true}`，仅对该会话启用；测试结束恢复 |
| POST `runtime/sessions/<id>/keyframe` | `{}`，明确请求关键帧 |

帧率诊断分别看 `source_reported_refresh_rate`、`source_observed_fps`、`source_frame_limit`、每路 `effective_fps` / `configured_fps` 与实际 `encoded_fps`。旧 `actualRefreshRate` 保留系统报告值，不能看到 60 就认定最新学习逻辑没有工作。

串流建立后，在工程根目录执行有界采样，例如主屏保持亮屏的普通虚拟屏基线：

```powershell
python tools/diagnose_virtual_stream.py --host 192.168.31.31 --tag tablet-next-baseline --seconds 90
```

需要主面板关闭采样时，另提供 `--adb <adb.exe绝对路径> --serial <已核对的主机序列号> --panel-off`；脚本 finally 尝试恢复主面板。实际系统休眠是不同测试，使用 `--sleep-main`，不与 `--panel-off` 同时使用。每次结束仍独立读取 API 与物理面板状态，不能仅凭 finally 推断恢复成功。

## 8. 已否决实验与操作约束

- 共享视频 socket 的**总 pacing**实验虽然减少最终发送失败，却让平板 120s 内新增 3086 帧队列丢弃、整帧发送 P95 恶化，已完整撤回。生产保留逐会话 pacing 与 FIFO 批次门。不要只凭“0 发送错误”恢复该实验。
- RTSP WFD PAUSE 的临时接口、协议 7 及测试改动均已撤回。实机 PAUSE 没有执行；生产保持协议 6，不能宣称已经省去系统 WFD 额外编码器。
- 系统最终 WFD 协商曾仍选择 1080p30，虽然接收端首选改为 60；独立镜像采集可达约 60fps。需要分别测量，不能相互替代。
- 过去有命令被工具自动审批返回 `blocked by policy`，未提供具体原因；这是执行工具拒绝，不能表述为用户拒绝或 Android 系统权限错误。未执行步骤不得记为测试结果，也不要换工具绕过相同拒绝。
- 用户已授权自主诊断、安装验证、提交推送代码和发布 APK；仍应遵守当前工具权限、保留现有用户数据，不清除 ADB 密钥、重置仓库或恢复已否决实验。
