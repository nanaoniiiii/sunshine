# 逐会话网络反馈与自适应控制

`v2026.10.12.3` 扩展固定 Android 原生引擎。参考 foundation-sunshine 的逐会话码率预算思想，接入固定 Moonlight common-c 的 `SS_FRAME_FEC_STATUS` 协议；当前版本由官方 Sunshine 提供协议发送、FEC 与控制通道，不替换客户端协议。

## 反馈和发送

原生控制通道接收 21 字节的大端 FEC 报告，校验 shard 数量、接收数量和多块索引。仅接受宿主近期发送的帧，最近 256 个帧/块键用于去重。报告包含恢复或未完成的块，采用尽力传送；没有报告不等于零丢包，不能把这些计数转换为全链路丢包率。

`GET /api/diagnostics` 的每个 `video` 会话新增：

- `control_rtt_ms`：ENet 可靠控制包的 RTT，超过五秒未更新为 null；不是视频端到端延迟。
- `fec_percentage` / `pending_fec_percentage`：当前与等待编码器接受的 FEC，pending 为 -1 表示没有待应用改变。
- `fec_reports`、恢复/不可恢复块计数、报告中的缺失数据包数、重复和拒绝计数、最近报告年龄。
- `nominal_video_fec_budget_kbps`、`control_ceiling_kbps` 与自动状态。

2026-10-16 排查发现，迁移到官方发送路径后，原有 pacing 策略没有实际接入逐包发送循环。现已在生成的 `videoBroadcastThread` 中接入：每帧最多连续发送 16 个数据报，按实际字节（含纠错包与协议前缀）累计纳秒期限，各 FEC 块共用期限，调度迟到不追赶突发。基础瞬时节奏取 `max(80000, 2 × 名义视频/FEC预算 + 500)` kbps；大帧另按约 20ms 目标估算，提升上限 160Mbps，已有更高的基础速率保留。它限制瞬时突发，不是测得的链路带宽或平均码率硬上限。将发送节奏压到平均编码码率附近会造成第二重排队，本机压力测试已观察到这种退化，因此不采用。

大帧按每块 255 个总 shard 的 Reed-Solomon 容量计算分块需求，在原有三块不足时使用协议支持的第四块。超出四块容量的帧仍沿用无 FEC 的发送路径，诊断 `fec_skipped_blocks` 明确计数，不能把配置了 20% FEC 当作每个大帧都受到纠错保护。

Android 10–13 串流期间同时请求低延迟与高性能 Wi-Fi 锁，主屏关闭时由高性能锁承接；最后一端断开时一起释放。仅持有低延迟锁不能覆盖这些系统上的息屏状态。Android 14 起高性能锁会映射到低延迟锁，重复获取不能绕过新系统限制，当前不额外获取重复锁。参见 [Android Wi-Fi 锁说明](https://developer.android.com/reference/android/net/wifi/WifiManager#WIFI_MODE_FULL_HIGH_PERF)。

Android 视频使用 `sendmmsg`，每批最多 16 个数据报。部分成功时只重试尚未发送的后缀；`EAGAIN/EWOULDBLOCK`、`ENOBUFS` 和中断进行有界重试，缓冲区压力重试间隔约 100µs，每批视频最多等待约 16ms，单个音频数据报最多约 8ms；调度延迟可能使实际等待超过该目标。成功的数据报不会重复发送，永久错误不重试。`send_syscalls` 记录实际系统调用数，`send_buffer_retries` 记录临时失败/中断重试次数，`send_errors` 记录最终失败包数；系统 `SndbufErrors` 包括后来重试成功的尝试，不能直接等同最终丢包数。

截止时间仅在实际临时发送错误后限制恢复，不因部分成功后的线程调度间隔直接漏发余包。成功前缀最多推进 16 次，不会无限循环。`last_send_errno` 保留最近一次最终失败的 errno（0 表示尚无记录），不是最近一次成功发送的状态；排查时同时看计数增量，避免把历史错误误认成当前问题。

多端共用的视频 UDP socket 请求约 1MiB 的 Linux 有效发送缓冲容量，不改系统全局网络参数，也不缩小已经超过该目标的 socket。内核可能限制请求，`socket_send_buffer_bytes` 报告实际 `getsockopt(SO_SNDBUF)` 数值。该容量包含内核记账开销，不等于可容纳同等数量的视频 payload；队列驻留限制也不涵盖内核中的包。此调整仍需同时核对接收端延迟，不能仅凭发送失败减少判断通过。

每个客户端有独立的视频/FEC 发送线程、帧队列和 pacing 期限，一路的大帧不占用另一路的整帧处理线程。多个线程共享协议端口的 UDP socket，通过 FIFO 批次门轮流提交最多 16 个包；只有该批重试占用门，不把 FEC 计算、帧排队或整帧 pacing 放进共享锁。音频沿用独立发送线程。编码、视频/音频发送和控制工作通过 Android 线程 API 请求显示优先级（nice -4），GL 分发线程也使用显示优先级；实际授权以设备为准，不修改系统全局调度和温控。发送线程请求较低 timer slack，以改善 pacing 等待精度。

控制通道补充截断、加密长度和明文长度校验；引用帧失效请求在不支持该原语的 Android MediaCodec 上转为 IDR 恢复。

原生 FEC 编译补回官方构建的 `autoshim.h` 强制包含，ARM64 使用 NEON。独立向量测试与标量测试核对相同 parity 和恢复结果。发送诊断增加准备帧、包头处理和线程 CPU 时间 P95，用于区分计算开销、系统调度等待和 socket 等待。引擎独立进程声明自身的 dataSync 前台服务并共用宿主通知；仅由宿主前台服务绑定不能保证厂商息屏策略把引擎继续视为前台进程。

## 控制入口

沿用会话 ID：

| 请求 | JSON 请求体 | 行为 |
| --- | --- | --- |
| `POST /api/runtime/sessions/{id}/fec` | `{"percentage":25}` | 0–35；手动请求关闭自动模式 |
| `POST /api/runtime/sessions/{id}/adaptive` | `{"enabled":true}` | 为当前会话启用反馈控制 |
| 同上 | `{"enabled":false}` | 停止自动调整，保留当前码率与 FEC |

手动设置码率也会关闭自动模式。重新连接的会话默认关闭自动模式；当前 FEC 不持久化为下一会话的设置。

FEC 调整先计算编码器目标，确保名义视频加 FEC 预算不增加，并遵守配置下限。编码器接受目标后才提交 FEC；拒绝时保留旧 FEC，并显示 `driver_rejected`。无可行预算时返回冲突。请以诊断中的已应用结果为准，HTTP 接受仅代表请求进入队列。

## 自动策略与边界

这是默认关闭的实验性反馈策略。收到有效丢失报告时，最多每两秒降码率 15%，可恢复块将 FEC 增加 2 个百分点，不可恢复块增加 5 个百分点，自动增加上限 35%。不超过协商视频预算，也不低于配置下限。提高冗余前等待编码器接受码率目标。

持续二十秒没有新的丢失报告，并且视频仍在输出、可靠控制 RTT 小于等于 100ms 且更新时间不超过五秒时，可每五秒谨慎探升约 5%（至少 100 kbps），同时将冗余缓慢恢复到连接初始值。这个探升条件是启发式；安静的报告通道不证明视频完全无丢包。没有新鲜 RTT、无视频输出或上一目标未被驱动接受时不探升。

2026-10-16 修复探升逻辑未接入实际编码命令循环的问题：原来只在策略测试中调用 `recover`，实机会降码率却不会按该策略回升。现由编码循环取命令时检查，要求最近两秒有编码输出、没有等待 IDR、上一驱动命令完成，并继续满足策略自身的 RTT、队列与冷却条件；诊断轮询不驱动控制。集成回归先复现缺失调用，再验证回升、待驱动确认、过期输出/RTT、IDR 恢复期和关闭自动模式的行为。

原生测试覆盖解析、过期/重复报告、序号环回、预算、降码率、冷却、驱动拒绝与探升。实际弱网收益必须用受控丢包和限速进一步对照；只在稳定局域网切换控制，不能证明弱网改善。

## v2026.10.12.4 修订

孤立损失观察、持续队列/RTT 压力回退、更严格的探升条件，以及防止大关键帧与有界队列互相触发恢复循环的有限 IDR 发送加速，见 [队列与编码器说明](queue-encoder-controls.md)。本版诊断补充实际接受的 UDP payload 和分阶段发送耗时。自动控制继续默认关闭。
