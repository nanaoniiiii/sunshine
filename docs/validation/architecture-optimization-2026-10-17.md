# v2026.10.17.5 优化与验证

版本代码 20261034，按使用者要求以正式版发布，并保留以下压力测试限制。v2026.10.17.4 在发现重连问题后已撤回为草稿，本页记录后续修复及验证范围。此次修改覆盖帧调度、输入几何、UDP 发送、首次授权和桌面退出生命周期。

## 架构、算法与线程

1. **GL 进度通知合批**：Binder 完成通知进入 FIFO mailbox，共享一次待执行 GL 任务，保留逐条通知顺序。回归覆盖发送完成先到、早期帧编码后到的竞态及多生产线程；没有修改跨进程回调协议，不宣称减少 Binder 事务。
2. **帧唤醒与额度**：保留已经足够早的 Handler 唤醒，减少反复取消和重新投递；直接扫描最早客户端截止时间，避免临时列表；用有序前缀清理过期额度，原位清理编码跳帧，保留已编码待发送帧。
3. **多端 UDP 线程公平性**：FIFO 发送门仅保护一次非阻塞 sendmmsg，单次最多 16 个数据报；EAGAIN／ENOBUFS 的 100 微秒等待放在门外，其他客户端可继续发送。保留 16ms 重试期限与部分成功后的前缀续发。
4. **输入几何缓存**：连续移动复用显示尺寸、旋转和 DisplayMetrics，显示事件与源切换使缓存失效；源显示或采集几何变化时取消旧触点，防止拖拽跨显示残留。
5. **内部管理直连**：本机 127.0.0.1 管理 API 显式使用 Proxy.NO_PROXY，外网更新保留正常网络策略。真实 loopback HTTP 测试验证不可达的系统 HTTP 代理不会阻断设置读取。

## 首次安装、录屏和 DeX 重连修复

- **正常断流保留引擎与录屏**：移除最后一路正常断开后自动重启健康引擎的路径；故障与 Binder 死亡恢复仍保留。三星上该误重启会导致 MediaProjection 被撤销，主页退回允许录屏。
- **首次授权按顺序进行**：录音／通知权限完成后再请求录屏；等待引擎前台状态建立，避免启动另一个仅 dataSync 的前台进程时触发三星 Android 13 录屏撤销。引擎通过 AIDL 同步有效录屏状态，声明相应前台服务类型。
- **DeX 退出后刷新界面根节点**：实机确认在旧状态中，接收端映射坐标落在按钮内，源端直接点击也不响应；仅重建 MainActivity 能恢复。新版在桌面退出完成后重建 UI，录屏、配对和串流由服务持有；不会因普通主屏息屏或初次空闲而重建。
- **等待三星旧显示销毁**：本机 DeX 接收端关闭后等待原生显示退出，避免快速重开时使用旧显示。检测到其他 DeX 显示时不关闭无关会话。
- **区分 Shizuku 授权与用户服务**：新 S20 曾出现主 Binder 可用、授权已给出，但管理器被三星后台策略限制，用户服务启动器取不到 provider，最终绑定等待 8000ms 超时。新版清理超时绑定、拒绝迟到回调，并提供打开管理器与解除后台休眠的具体提示。首次安装仍需正常授权，不能跳过系统权限。
- **首次 DeX 确认改为 3 分钟**：保留三星设备列表、立即开始与首次使用说明的交互时间，显示当前准备阶段；实际等待超过旧版 60 秒后再确认已成功。
- **全屏旋转命令兼容**：从本机 wm help 识别 user-rotation／set-user-rotation 和固定旋转命令，修复 Android 13 使用旧命令造成全屏切换与恢复失败。
- **状态一致性**：主屏息屏模式报告 mainPanelOff=true；过期的引擎连接不能把新一代的就绪状态置为真。

实现依据包括项目实机日志、[Android MediaProjectionManager](https://developer.android.com/reference/android/media/projection/MediaProjectionManager)、[AOSP WindowManagerShellCommand](https://android.googlesource.com/platform/frameworks/base/+/a42e14ce6379/services/core/java/com/android/server/wm/WindowManagerShellCommand.java)、[Android Handler](https://developer.android.com/reference/android/os/Handler)、[DisplayManager](https://developer.android.com/reference/android/hardware/display/DisplayManager) 和 [sendmmsg](https://man7.org/linux/man-pages/man2/sendmmsg.2.html)。

## 双端压力结果与限制

SM-G9860 原生 DeX → OPPO 1440×3168 HEVC / 50Mbps，与 Windows 2560×1440 H.264 / 实际视频预算约 15Mbps 同连。原生桌面 60Hz，主屏物理面板关闭，窗口内滚动随机噪声 30 秒：

| 项目 | OPPO 路 | Windows 路 |
| --- | --- | --- |
| 编码窗口 FPS 中位数 | 59.9745 | 59.9288 |
| 新增编码帧 | 1787 | 1786 |
| 新增队列丢帧 / 发送失败 / 提交超时 | 0 / 0 / 0 | 0 / 0 / 0 |
| 控制 RTT 窗口中位数 | 4ms | 5ms |

该数据不是端到端延迟。Windows 实际画面与性能叠加层可见，观察瞬间报告 Loss 0.00%，不能外推整个测试的真实全局丢包率。

随后全屏随机噪声更重的 30 秒测试中，温控等级为 3，编码帧窗口中位数降至约 17–18fps，两路新增队列丢帧 267／276、提交超时 97／70，发送失败仍为 0。大帧发送耗时显著上升并伴随温控限制，说明该组合不能稳定处理这一极端负载。不能把全屏随机噪声测试写成通过，也不能把源端主动丢帧直接等同于网络丢包；本版没有消除固件、编码硬件、温控和带宽上限。

停止压力源后继续完成兼容桌面、主屏息屏和退出测试，功能可恢复。主屏息屏双端短测中，手机路编码窗口中位数约 87.46fps，电脑路约 59.99fps，均无新增队列丢帧或提交超时；这也不是双端稳定 120fps 证明。

前一 .4 单端静态 2K／60fps 测试曾得到 3600 条进度通知合批为 3009 次 GL 处理、复用已有唤醒 1815 次。约减少 16.4% 的任务投递衡量的是通知处理任务数量，不是 CPU、帧率或端到端延迟改善百分比。缺少有效旧版性能对照，不发布提升百分比。

本轮没有完成三端同时高动态、长时间息屏、平板与所有三星固件矩阵、所有外设手柄、多点手势、音画同步听感等验收。原始日志和截图保留本地 work，不上传设备抓取、配对资料或厂商 APK。
