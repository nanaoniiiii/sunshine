# 虚拟屏高丢帧与高延迟：定位、修正与实测

2026-10-16，Samsung SM-G986U1 / Android 13 / One UI 5.1，无 HDMI。用户报告手机接收分辨率 1440×3168、电脑 2K，普通虚拟屏和原生 DeX 都会出现。此次端到端接收端为 Windows Moonlight，分别请求 1440×3168 和 2560×1440；手机接收端未重新连接 ADB，因此没有把它写成已完成客户端实测。

## 原因与证据

### 1. 虚拟源只有 60Hz，宿主仍按 120fps 编码旧纹理

调度器原先只取客户端 FPS 和配置上限，没有使用虚拟屏的实际刷新率；启用补帧时，源帧尚未到达也会再次编码旧纹理。普通虚拟屏和 DeX 的采集最终共用这条 GL/MediaCodec/发送路径。

本机系统为两种虚拟屏都只公布 60Hz，但诊断曾同时显示 `actualRefreshRate=60`、target `effective_fps=120`。在 2K 复杂动态画面、120fps 请求的同一会话中，仅关闭补帧，20 秒的编码输出从约 2250 帧降到 1205 帧，队列丢弃从 997 帧降为 0，可靠控制 RTT 仍约 3–8ms。这证明额外重复工作能把高分辨率处理队列推入过载，不是必须启用 DeX 才发生。

最初故障快照还记录：Moonlight 显示约 73% Loss，宿主编码提交到输出 P95 约 204ms、累计队列丢弃超过 2000 帧，控制 RTT 约 8ms。宿主主动清除参考链会产生帧编号缺口，客户端的损失显示不能全部解释为路由器丢失了已发出的 UDP 包。

### 2. UDP 实际发送路径没有 pacing，临时缓冲区不足会直接弃包

`prepare_source.py` 原先虽替换了官方 Sunshine 的发送循环并增加计数，却没有接入仓库已有的 pacing 策略。Android `platf::send()` 只重试中断，遇到 `EAGAIN/ENOBUFS` 等临时发送缓冲区压力直接返回失败。高分辨率完整桌面的大帧及 FEC 会放大突发。

在 1440×3168 的一次 20 秒对照中记录了 713 次最终 UDP 发送失败。随后核对一个连续区间，系统 `Udp SndbufErrors` 从 274644 增至 275477（+833），会话累计 `send_errors` 同期从 784 增至 1617（+833）。这些包是在手机发送端被拒绝，不能归因于接收端解码器。

这不意味着所有网络损失都来自发送端；计数只证明本次复现中存在明确的本机弃包路径。

## 最终实现

- `FramePacer.effectiveFps()`：虚拟屏遵守系统实际刷新率及客户端/配置上限；未知虚拟刷新率保守按 60Hz。真正提供 120Hz 的源仍可达到 120 的送帧上限。主屏路径保持原策略，退出虚拟屏后已实测恢复 120 的上限。
- `nextSubmissionNs()`：虚拟屏优先等待新纹理，避免先编码旧纹理再错过紧接着到达的新帧。静态画面启用补帧时约每 250ms 保活，新纹理到达会重新调度；不需要将用户的全局补帧选项永久关闭。
- 实际视频逐包发送循环接入有界突发 pacing，各 FEC 块共享同一帧的字节期限，最多连续 16 包，计入真实数据报大小。瞬时速率与关键帧提升策略详见 [网络反馈说明](../network-feedback.md)，不把它当作测得的链路带宽。
- 数据报完全拒绝时才进行短时重试；永久错误与短写不重发，成功数据报不重复发送。每包重试目标上限约 8ms，调度可能使实际等待更长；不会无限等待。
- 诊断补充 `send_buffer_retries`，并让 pacing 与整帧发送耗时来自实际发送路径。

编码器仍使用原来的 VBR 模式。CBR 和过紧的 pacing 在探索测试中增加了关键帧/队列积压，没有保留为最终方案。发送线程请求较低 timer slack 用于 pacing 精度，但本机读到的原值为 50000ns，未把它认定为本次故障的主要原因。

## 最终本地包复测

保持 `repeat_frames=true`、`max_stream_fps=240`，客户端请求 120fps。虚拟源实测 60Hz，最终动态输出约 60fps。请求码率 14000kbps，协议诊断的协商视频码率约 10508kbps，FEC 和协议开销另计。

复杂画面使用独立、无权限的诊断 APK：持续滚动彩色噪声，覆盖高熵动态负载。下表按各测试窗口的计数差值统计，包含硬件/调度波动，不能据此保证所有场景零丢包。

| 最终场景 | 窗口 | 编码输出 | 队列丢弃 | 最终 UDP 失败 | 内核 SndbufErrors |
| --- | --- | --- | --- | --- | --- |
| 普通虚拟屏，1440×3168，高熵动态画面 | 20s | 1193 帧 | 0 | 0 | 0 |
| 普通虚拟屏，2560×1440，高熵动态画面 | 25s | 1497 帧 | 27 | 0 | 0 |
| 原生 DeX，2560×1440 采集，动态计数器 | 20s | 1186 帧 | 0 | 0 | 0 |
| 普通虚拟屏，2K 静态保活 | 10s | 40 帧 | 0 | 0 | 未采样 |

手机目标分辨率动态测试的编码提交到输出 P95 样本中位数约 35.24ms；2K 高熵画面约 30.70ms；DeX 动态计数器约 28.83ms。它们是编码提交到输出的局部测量，不是输入到屏幕的完整延迟。DeX 计数器场景的发送前队列 P95 约 2ms，控制 RTT 约 4–7ms。

2K 高熵压力测试仍有 27 帧队列丢弃，较未限制重复编码的 997 帧/20s 明显减少，但不能宣称高负载问题已完全消失。最终各窗口的最大统计还可能包含过渡期；应同时检查每秒 JSON，而不是只看累计计数或某一张截图。

静态保活未断流，退出虚拟屏后主屏 target `effective_fps` 恢复 120；原生 DeX 的创建与动态采集通过。测试结束关闭独立诊断应用，保留原生 DeX 桌面。
