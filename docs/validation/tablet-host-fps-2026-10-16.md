# SM-T970 主机：虚拟屏实际帧率与交付候选验证

记录日期：2026-10-16。版本 `v2026.10.16.1`，versionCode `20261028`。

## 结果与适用范围

SM-T970 / Android 13 作为 Sunshine 主机，Windows Moonlight 接收普通虚拟屏的 2560×1440 / 120fps H.264，名义视频预算 14988kbps，自适应关闭。本轮不是原生 DeX，也没有关闭主屏面板。

修复前，测试源实际每秒绘制约 115–120 帧，采集约 119fps，但虚拟 Display 报告 60Hz，使编码器被配置为 60fps，编码 FPS 窗口中位数约 59.95。修复后根据连续新纹理时间戳确认 120fps，保持系统报告值不变，将实际编码上限提升到 120。

最终候选连续采样 90 秒，91 个样本（包含学习与重配阶段）：

| 指标 | 结果 |
| --- | --- |
| 系统报告刷新率 | 60Hz |
| 识别后的源上限 / 编码配置 | 120fps |
| 编码 FPS 窗口最小 / 中位 / 最大 | 28.99 / 118.64 / 120.70 |
| 新增编码帧 | 10423，整个区间平均约 115.81fps |
| 新增队列丢帧 / 最终发送失败 / 输入额度超时 | 0 / 0 / 0 |
| 提交到编码输出 P95 的窗口中位数 | 23.61ms |
| 整帧发送 P95 的窗口中位数 | 1.36ms |
| 发送 socket 实际缓冲 | 1048576 字节 |
| 温控状态采样 | 0，末段为 1 |

本轮源内容简单，实际编码码率窗口中位数约 1400kbps，峰值编码帧约 46KB。它验证了错误限帧的修复，不代表固定 50Mbps、高熵噪声、三客户端或端到端显示延迟已通过。发送失败为零表示本机发送路径未报告最终错误，不证明网络接收端零丢包；P95 也不是端到端延迟。含启动阶段的最小 FPS 明确保留，不称全程满帧。

## 实现与回归

- `SourceCadenceTracker` 使用 SurfaceTexture 时间戳，连续两个稳定窗口确认更高源节奏，重复、倒退和大间隔样本不作为高刷依据；换源重置。
- 维持系统报告值、观察帧率和应用上限三个诊断量，避免把客户端请求值当作实际结果。
- `VirtualDisplayUserService` 增加旧版 Shizuku 12 需要的无参构造入口；保留现代 Context 构造路径。平板 Shizuku 12.9 真机已成功创建虚拟屏。
- 88 项 Release JVM 测试全部通过，失败、错误和跳过均为 0；Release lint 和三种 APK 构建通过。原生代码沿用已在两种 ABI 各执行 11 项测试通过的自适应回升修复，随后修改仅在应用层。
- 三个 APK 均校验包内 `libsunshine.so` 与仓库相应 ABI 文件逐字节一致；签名检查另见发布交接。

## 未完成与环境因素

1. 最新候选未完成平板主机的两路／三路同连、主面板关闭、退出重连和长时间高动态负载测试。OPPO 的新主机配对没有完成，不归入本轮通过范围。
2. 旧三星手机主机的原生 DeX 三端测试曾出现约 30fps 和高熵启动期丢帧，见 [历史记录](multi-client-virtual-screen-2026-10-16.md)。本次普通虚拟屏修复不能证明其全部解决。
3. 平板上另一个屏幕服务占用了 Sunshine 相同端口，启动前已将该应用 force-stop；未卸载、禁用或清除其数据。同时运行会造成端口冲突。
4. 平板同时有 Shizuku 与 Stellar；发现 Stellar 守护进程重复 ClassNotFound 异常，未修改该第三方程序，也未证明它是帧率问题的原因。
